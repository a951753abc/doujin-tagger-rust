## DEC-003 語料盤點

以目前 13,566 筆收藏做只讀檔名形狀盤點，找到 13,162 筆可用的 leading bracket 候選：

| 形狀 | 筆數 | 說明 |
|---|---:|---|
| `社團 (作者)` | 10,131 | 可由最外層尾端括號拆成社團與作者候選 |
| `社團` | 3,012 | 沒有作者括號 |
| 巢狀、不完整或其他括號形狀 | 19 | 不適合用現有單一 regex 強制拆解 |
| 含逗號或頓號的多人作者 | 至少 412 | 是 `社團 (作者)` 的子集合 |

已確認規則：

1. 平衡的最外層尾端括號拆成社團與作者區段。
2. 作者在 domain model 中保存為清單，同時保留作者區段原始字串。
3. 只以 `、` 與 `,` 自動拆分多人作者；其他符號不拆。
4. 同人誌／CG 的單一 bracket 視為社團，商業誌的單一 bracket 視為作者區段。
5. 巢狀作者括號不遞迴拆解。
6. 括號破損或不在尾端時不由 filename parser 硬猜；保存原文並嘗試外部補足，外部結果仍不可靠時才送人工確認。

## DEC-005 白話說明

假設檔名寫的是：

```text
[社團] 某作品 (ポケモン).zip
```

而系統的正式名稱表認為 `ポケモン` 應統一顯示成 `ポケットモンスター`，有兩種保存方式：

### 選項 A：只保存正式名稱

```text
原作 = ポケットモンスター
```

優點是資料簡單；缺點是之後看不出原檔名實際寫了 `ポケモン`，也較難追查 parser 為何轉換。

### 選項 B：原始值與正式名稱都保存

```text
檔名解析值 = ポケモン
正式原作 = ポケットモンスター
```

優點是可追溯、可以重建 canonical mapping，也方便未來修正別名規則；缺點是資料模型多一層。

決策採用選項 B：同時保存原始值與 canonical 正式名稱。

## DEC-007 適用方式

優先序用於多個來源對同一欄位提出值時，決定哪個值成為目前有效值：

```text
手動修改
  > 外部 metadata
    > 檔名解析
      > 推斷結果
```

此決策不等於允許外部 metadata 自動寫入；「是否需要人工確認」與 confidence 門檻仍是另一項待決政策。

## 2026-08-11：掃描與檔案生命週期決策

### 消失路徑與人工裁決

當既有收藏的路徑消失，且掃描發現一筆或多筆同名候選時：

1. 舊收藏不再顯示於有效 Library，但以 tombstone 保存原 metadata 與 tags。
2. 同名本身不是同一檔案的充分證據，不論候選是否唯一，都不得自動遷移 metadata。
3. 所有候選收藏保持獨立，直到收藏管理者完成人工裁決。

### 搬移與刪除

1. 後端只允許將下載區收藏搬到已設定的歸檔區。
2. 批次搬移允許部分成功；失敗項目保持原狀，結果必須逐筆可辨識。
3. 軟刪除與永久刪除都必須由收藏管理者明確選擇並確認。
4. 軟刪除將檔案送到作業系統資源回收桶，從有效 Library 隱藏收藏，並保留可供還原的 tombstone、metadata 與 tags。
5. 永久刪除不經資源回收桶，並永久移除收藏索引與 tag 關聯。

## 2026-08-12：Metadata 建議與名稱合併決策

### 建議覆寫與人工裁決

1. 場次、社團、作者、原作等欄位使用相同的來源優先序，不再讓原作具有特殊覆寫行為。
2. 外部 metadata 可以取代檔名解析或推斷結果，但不能自動取代手動值。
3. 使用者可以明確選擇以外部候選取代手動值；系統必須把這次選擇記錄為手動裁決，同時保留外部來源與先前值。

### Confidence 與自動套用

Confidence 採 0 到 1 的綜合分數，至少包含以下可追溯資訊：

- 來源可靠度
- 識別碼匹配
- 字串相似度
- 規則確定度
- 總分與人類可讀的判斷理由

自動處理級距：

1. 總信心度至少 0.95、具有可靠識別碼完全匹配且沒有手動衝突時，才可自動套用已驗證欄位。
2. 總信心度介於 0.75（含）至 0.95（不含）時，只顯示為待確認建議。
3. 總信心度低於 0.75 時，不提供為可直接套用的建議，但保留搜尋紀錄供追查。
4. 高總分但沒有可靠識別碼完全匹配時，仍需人工確認。
5. 外部結果只有部分欄位可靠時，只處理那些欄位；不要求整筆全有或全無。

### Canonical 與拒絕合併

1. 已確認的官方名稱優先成為 canonical，不因是否為日文而改變。
2. 沒有官方名稱時，系統可以依語言、使用次數與其他證據提出推薦，但不應因此自動合併。
3. 使用者拒絕一組名稱合併後，系統應保存「不得合併」規則，直到使用者主動移除。

## 2026-08-12：本機 UI、縮圖與安全邊界決策

### 本機狀態與網路邊界

1. 最近開啟紀錄是瀏覽器本機狀態，不需要跨瀏覽器或裝置同步。
2. 服務只能監聽 IPv4 或 IPv6 loopback；若設定要求監聽非 loopback 位址，啟動必須失敗並回報原因。
3. Rust v2 保留作業系統預設開啟與指定閱讀器閱讀兩種動作。

### 縮圖重試與重建

1. 暫時性縮圖錯誤應安排未來重試；連續失敗時增加等待時間，避免無限密集重試。
2. 不支援格式或確定損壞等永久性錯誤不進行定時重試；檔案變更或使用者手動要求時才重新嘗試。
3. 縮圖尺寸或品質變更後，自動將既有縮圖標記為需要重建並排程處理。
4. 收藏管理者也可以隨時手動要求重建縮圖。

### 縮圖前端生命週期

1. Library 第一次取得 pending 或 running placeholder 後，必須自動追蹤同一收藏，直到真正的 ready WebP 可以顯示；不得要求收藏管理者重新整理頁面。
2. 清單與詳細資料同時顯示同一收藏時，共用一份追蹤工作，避免重複密集要求。
3. 畫面換頁、重新搜尋或詳細資料改綁其他收藏後，舊工作的完成結果不得覆寫新的畫面內容。
4. 暫時性失敗依後端提供的 next retry time 恢復追蹤；永久性失敗停止自動要求，詳細資料仍提供手動重建。
5. ready、永久性失敗或畫面已不再使用該收藏時，前端必須停止對應的追蹤工作。

### 手動清空 metadata

手動清空欄位代表移除目前的手動值，而不是保存一個會阻擋其他來源的空白值。系統隨後重新套用既有優先序；若仍有外部 metadata、檔名解析或推斷候選，最高優先候選可以重新成為有效值，否則欄位保持空白。

## 2026-08-12：Shadow comparison 正規化決策

完整收藏的唯讀 shadow comparison 產生 DEC-023 至 DEC-029：

1. Percent decoding 只做一次；只有新收藏成功解析出結構，且解碼後名稱是安全、無衝突的單一檔名時，才實際重新命名 ZIP。重新命名成功後才用新路徑建立索引；任何失敗都保留原檔，禁止覆寫。
2. `[名稱@來源]` 必須有後續收藏結構支持才是 source marker，並保存原文。
3. Parser 保存底線與標題中的全形括號字形；搜尋用正規化不得回寫 metadata。
4. 已知方括號標記採完整內容匹配；未知尾端標記保存在 other info，且不得阻擋前方已知標記或原作候選。
5. [Parser Corpus 審閱批次 06](../parser-corpus/review-batch-06-shadow-normalization.md) 的七筆案例已獲確認，將納入 accepted corpus。

## 2026-08-12：Rust v2 儲存模型決策

[儲存模型 Example Mapping 批次 07](workshops/storage-v2-example-mapping.md) 已全數接受：

1. SQLite 保存 catalog 與可查詢狀態；ZIP 留在檔案系統，縮圖只作為可重建 cache。
2. 收藏身分與位置歷史分開；只有系統明確完成的 move 可以沿用收藏 ID，scanner 不以同名猜測身分。
3. Metadata 保存有來源的候選及每欄目前選擇；清除手動值後依既有候選重新選擇，不建立手動空字串。
4. Raw 名稱、canonical entity、alias 與拒絕合併規則分開保存，不改寫歷史 parser payload。
5. Tombstone 保存 metadata、tags、位置與候選關聯，直到人工裁決。
6. Effective metadata 與 FTS 是可重建投影，不能取代候選、選擇與人工裁決等權威資料。
7. 寫入經單一 repository writer 與 transaction；同一收藏的資料變更一起成功或 rollback，失敗必須明確回報。
8. v2 使用新的 `doujin-v2.db`，從舊資料庫唯讀匯入、驗證並保留 rollback 路徑，不做原地升級。

## 2026-08-12：Tombstone 身分合併決策

[Tombstone 身分合併 Example Mapping 批次 10](workshops/tombstone-consolidation-example-mapping.md) 已全數接受並記錄為 DEC-038：

1. `confirmed` 只保存人工確認，不立即改變收藏身分或資料。
2. 明確 consolidation 後由較早的 tombstone ID 存活，接管 candidate current location；實體檔案不搬移。
3. Tags 採聯集，雙方 parser、metadata、外部結果與位置證據均保留，且可追查原 collection ID。
4. Tombstone 原有選擇預設保持；不同手動值必須先逐欄選擇 tombstone 或 candidate。
5. 多候選必須恰有一筆 confirmed，其餘全部 rejected。
6. 全部 catalog 變更在單一可重試 transaction 完成；任一步驟失敗全部 rollback。
7. Merged candidate 保留指向 survivor 的 audit，不提供未經獨立 BDD 定義的自動拆分。

## 2026-08-13：DLsite 書名搜尋決策

1. 最新 parser 證據具有唯一 typed RJ 時，繼續優先執行精確產品查詢。
2. 沒有 RJ、但收藏具有辨識書名時，以書名查詢 DLsite 搜尋頁；長標題可使用常見分隔符前至少四字的穩定核心書名作為查詢字串。
3. 只有正規化後恰好一筆完全相符的搜尋結果可以繼續查詢產品；零筆或多筆同名都不得依搜尋排名猜測。
4. 書名匹配不是可靠識別碼完全匹配，因此取得的 metadata 只能成為待確認建議或搜尋紀錄，不得自動套用。
5. 沒有 RJ 也沒有非空白書名時不送出外部要求，並回報 unsupported。

## 2026-08-13：外部候選冪等性決策

1. 相同收藏、欄位、JSON 值、來源參照、confidence 分數與證據內容共同構成同一外部候選。
2. 重複搜尋到同一候選時重用既有 assertion，不新增第二個可裁決項目。
3. 每一次外部搜尋結果仍個別保存，讓背景工作與查詢時間可以追查。
4. 已採用的候選保持採用；已拒絕或 obsolete 的候選不得因重複搜尋重新成為可用候選。
5. 讀取既有資料時，相同外部 assertion 只顯示選中或狀態順位最高的一筆，避免歷史重複資料污染 UI。

## 2026-08-13：E-Hentai／ExHentai metadata 與標籤決策

1. E-Hentai 與 ExHentai 共用 gid/token gallery identity 與 gdata 模型；具有唯一 typed identity 時直接查詢，否則以辨識書名搜尋。
2. 書名搜尋必須以 gdata 的 `title` 或 `title_jpn` 核對；去除社團前綴後只能有一筆完全相符，翻譯尾綴不得被視為原始作品的完全匹配。
3. `group`、`artist`、`parody` 分別映射社團、作者、原作；`parody:original` 的 canonical 值為「オリジナル」。
4. `character`、`female`、`male`、`mixed`、`other`、`language` 以 `namespace:value` 保存為 additive collection tags；不得覆寫人工 metadata，重複搜尋保持冪等。
5. 書名匹配的 metadata 保持 suggestion；唯一 gid/token 完全匹配才可依 DEC-015 進入自動套用。一般 tag 必須至少達 suggestion 信心度才可加入。
6. production 預設使用公開 E-Hentai；只有本機明確提供 `DOUJIN_EXHENTAI_COOKIE` 時才搜尋 ExHentai，且 cookie 不得記錄或回傳 UI。
7. Provider chain 以 E-Hentai 為主，DLsite 只查 E-Hentai 未覆蓋的欄位；fallback 的 no-match 不推翻已取得的 E-Hentai 結果。

## 2026-08-13：DLsite 場次 fallback 決策

1. 場次值 `DL` 的語意是作品已由 DLsite provider 成功匹配，但 DLsite 商品沒有提供更明確的活動 option。
2. `[DL版]`、`[Digital]` 或 `is_dl = true` 只描述數位版狀態，不能作為 DLsite 來源證據，也不能推斷 `場次 = DL`。
3. DLsite response 有明確活動 option 時優先使用該活動，不改成 `DL`。
4. 以唯一 typed RJ 匹配時，`DL` 候選可依 DEC-015 評估自動套用；只以唯一完全相符書名匹配時仍是 suggestion，必須人工採用。
5. E-Hentai／ExHentai 可以提供 metadata 與 tags；若其缺少場次，provider chain 只把場次交給 DLsite 補足。DLsite no-match 時場次保持空白。
6. 先前由 `is_dl` 錯誤推斷的 inference 必須精準撤回；不得刪除或覆寫其他人工、外部、檔名與 legacy 場次。
